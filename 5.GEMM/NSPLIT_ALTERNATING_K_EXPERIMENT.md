# Alternating K64/K128 stage experiment

## Goal

Keep the current `M256 x N256` output tile and two independent `N128`
consumer pipes, but reduce TMA issue and barrier overhead without increasing
shared-memory capacity.

## Layout

Logical stages alternate by K depth:

| stage slot | A tile | B0 tile | B1 tile | total |
|---|---:|---:|---:|---:|
| even (`slot 0`) | `256 x 64` | `64 x 128` | `64 x 128` | 64 KiB |
| odd (`slot 1`) | `256 x 128` | `128 x 128` | `128 x 128` | 128 KiB |

The two slots consume 192 KiB in total, equal to the canonical three-stage
`K64 + K64 + K64` ring. Each K192 interval changes from three logical stages
to two:

| K interval | canonical 3 x K64 | alternating K64/K128 |
|---|---:|---:|
| TMA transactions (A/B0/B1) | 9 | 7 |
| producer commits | 3 | 2 |
| consumer wait/commit groups per pipe | 3 | 2 |
| shared-memory reuse distance | K192 | K192 |

The K128 A slot is composed from two K64 TMA transfers attached to one
completion barrier. This preserves the kernel's validated SW128 A layout.
B0 and B1 each use one K128 TMA transfer, so the long stage needs four TMA
transactions rather than six. The K128 MMA stage executes eight K16
instructions per N128 pipe instead of four.

## Controlled comparison

- GPU: one NVIDIA B200.
- Baseline: `baseline/gemm256_bf16_16k.cu` from the same commit.
- Candidate: generated by `generate_gemm_nsplit_alternating_k.py`.
- Correctness: full C validation at `M=N=K=512`, both `pattern` and `ones`.
- Performance: `M=N=K=16384`, inputs `[0,1)` and `[-8,8)`.
- Timing: one warmup and five measured iterations per process.
- Run baseline and candidate in interleaved AB/BA order to reduce thermal
  ordering bias.
- Record compiler resources and SASS instruction counts in addition to
  TFLOP/s.

## Decision rule

Do not replace the canonical kernel unless correctness passes and the
candidate produces a repeatable improvement outside ordinary run-to-run
noise. Preserve negative results as an ablation.
